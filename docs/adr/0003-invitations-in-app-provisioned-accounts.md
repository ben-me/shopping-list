# 0003 - Invitations are in-app; accounts are provisioned; no outbound email

The MVP originally assumed invitations were delivered by email and that the app had a public sign-up. The app is private by design, though: it serves exactly the people whose accounts exist in D1 — a household. There is no email provider, no SMTP/IMAP, and standing one up is maintenance nobody wants, so the app never sends anything outside itself.

We chose: **no outbound notification of any kind** (no email, push, digest, SMS), and invitations target **existing users only** — the Owner invites by the email of an account that already exists, and delivery is purely in-app: the invitee sees pending Invitations when signed in and accepts or declines. Accepting makes them a Member with equal edit rights; a decline records the Invitation as `revoked` so it leaves both pending lists (a distinct `declined` status is deferred). The `token` column is retained but unused — it reserves a future email/join-link path with no migration if the app ever reopens.

Because there is no public sign-up, accounts must come from somewhere. We chose: a **one-time bootstrap** — sign-up is available only while the user table is empty and creates the first account, the **Admin**, who then provisions everyone else through an admin-only route built on better-auth's server-side user creation, so password hashing stays with better-auth (never raw SQL into D1). After the first user exists, sign-up is closed server-side via better-auth's `disableSignUp` and hidden in the UI. The Admin holds no special rights inside a List. Public sign-up could return later by re-enabling the switch; until then, provisioning is the only door in.

Chosen over delivered invitations (needs an email provider and a join-link flow) and over raw-SQL user creation (forces reimplementing better-auth's password hashing) because the app is a two-person household tool where in-app delivery and better-auth-managed accounts cover the entire need with no external dependencies.
